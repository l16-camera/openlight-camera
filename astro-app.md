# Отдельное астро-приложение для L16

Статус: **решение принято 17.08.2026, первая половина доказана на железе, вторая нет.**
Идея пространственного стекинга, ради которой всё затевается, — в [astro-mode.md](astro-mode.md).

## Почему отдельное приложение, а не ещё один режим

Колесо режимов и так разрослось, а нужды астро ортогональны штатным: не нужны автофокус,
замер, вспышка, склейка и прокси-JPEG; нужны ночной интерфейс, интервалометр, расчёт смаза
и — главное — **выбор того, какие модули стреляют и с какими параметрами**.

Последнее не косметика. Сегодняшние кадры показывают, что модуль A1 экспонируется **иначе
остальных**: усиление 3.88× против 7.75×, в старых кадрах выдержка 2.57 мс против 5.13 мс.
Штатная логика бережёт опорный модуль ради склейки. Для сложения по пространству эта
асимметрия — прямой дефект: пять модулей обязаны быть сняты одинаково, иначе складывать их
нечестно. Починить это можно только там, где формируется запрос.

## Роли модулей

| модуль | роль | предел по смазу (NPF) |
| --- | --- | --- |
| **A2**, 28 мм, панхром | плейт-солвинг | ~28 с |
| **C6**, 150 мм, панхром | точное наведение, контроль фокуса | ~6 с |
| A1, A3, A4, A5 | сложение по пространству — сам снимок | ~28 с |

Панхром для плейт-солвинга не «немного лучше», а качественно другое. Солвер выбрасывает
цвет и работает по серому, так что мозаика — чистый убыток. Звезда это точечный источник:
на байеровском модуле её видит один пиксель из четырёх, остальные три её не измеряли, и
демозаик дорисовывает недостающее. Центроид уезжает, причём **по-разному для красных и
синих звёзд** — систематическая ошибка, зависящая от спектра объекта. На панхроме каждый
пиксель настоящий отсчёт, интерполяции нет, плюс около ступени глубины.

Реальные фокусные считаны из заводских интринсик: у модуля 28 мм это 3380 px × 1.1 мкм ≈
**3.7 мм**, у 150 мм — 18700 px × 1.1 мкм ≈ **20.6 мм**. Отсюда и пределы по смазу; диафрагмы
взяты справочные (f/2.0 и f/2.4), при других числа поедут.

### Ограничение, которое придётся обойти или принять

Состав захвата меняется по фокусному, парами групп — это вендорные конфигурации
`frame_size_ab`, `frame_size_bc`, `frame_size_c`:

- 28 мм → пришли A1–A5 и группа B, **ни одного C**;
- 75 мм → группа B и C1–C6, **ни одного A**.

Значит **A2 и C6 в один кадр не попадают никогда**, и широкий солвер с длинным наведением
одновременно, как оно есть сейчас, не снять. Может ли своё приложение задать произвольный
набор модулей — неизвестно.

## Что доказано на железе

Пробник в [astro-probe/](astro-probe/) — APK на 17 КБ, написанный с нуля, без родства со
штатным приложением. Собирается без Gradle: `sh astro-probe/build.sh` (javac → d8 → aapt2 →
zipalign → apksigner).

**Привилегии не нужны.** Наша сборка стоит в `/data/app`, не в `/system/priv-app`, и снимает
полноценные кадры. Пробник, поставленный туда же обычной установкой, открывает камеру,
собирает сессию, ведёт превью 3840×2160 и выполняет захват. В манифесте нет ни одной
`uses-library` и ни одного системного разрешения — только `CAMERA` и запись на карту.

**Вендорные теги доступны, но не перечислены.** В `getAvailableCaptureRequestKeys()` их
**ноль**; собирать приходится рефлексией через скрытый конструктор
`CaptureRequest.Key(String, Class)` — ровно так же делает и штатный SDK
(`openlight/co/lightsdk/camera2/KeyMapperInternal`). На Android 6 запрета на такую рефлексию
ещё нет.

Полный список вендорных тегов, вынутый из штатного SDK:

| запрос | тип | | результат | тип |
| --- | --- | --- | --- | --- |
| `co.light.zoom_factor` | Float | | `co.light.stacked_capture_fw` | Byte |
| `co.light.iso_range_min/max` | Integer | | `co.light.tripod_fw` | Byte |
| `co.light.shutter_range_min/max` | Long | | `co.light.stacked_capture_total_size` | Integer |
| `co.light.focus_type` | Integer | | `co.light.stacked_capture_num_transfers` | Integer |
| `co.light.stacked_capture_state` | Byte | | | |
| `co.light.burst_fps` | Integer | | | |

Отдельно: `co.light.tripod_fw` — ключ **результата**, то есть камера сама сообщает состояние
штатива. Для астро это прямо интересно, семантика не выяснена.

**HAL объявляет о себе больше, чем показывает приложение:**

```
выдержка:                      10 449 … 29 981 853 000 нс   (то есть до 29.98 с)
ISO:                           100 … 12800
предел аналогового усиления:   ISO 775
```

Последняя строка независимо подтверждает замер по кадрам, где усиление упиралось в 7.75×.
И важное: **реальная съёмка режется на 19.45 с, что ниже объявленных HAL 29.98 с** — значит
ограничение стоит не в HAL, а под ним.

## Чего пробник не смог, и что из этого следует

Кадра он не получил. Перебраны `CONTROL_CAPTURE_INTENT` = 2 и 6…13 (включая вендорные 11 —
перекачка серии, 12 — шесть кадров, 13 — три) вместе с `co.light.stacked_capture_state = 1`.
Каталог остался с теми же 228 файлами. **Съёмка запускается не одиночным `capture()` по
шаблону `STILL_CAPTURE`.**

Путь снимка в штатном приложении прослежен:

```
CaptureManager.takePicture()
  → CaptureReqManager.startCapture(previewBuilder)
      → AutoExposureManager.preCaptureTrigger(previewBuilder)
      → CameraManager.triggerCaptureToHal()      // только меняет состояние сессии
  → CameraManager.startCaptureRequest()
      → mCaptureSession.capture(mPreviewRequestBuilder.build(), …)
```

То есть спуск — это одиночный захват **того самого билдера превью**, который крутится в
повторяющемся запросе и накопил все ключи режима, после взведённого `AE_PRECAPTURE_TRIGGER`.
Изображение через поверхности не приходит вовсе: в сессии одна поверхность превью, ни одного
`ImageReader` во всём приложении нет, а `.lri` пишет сам ASIC в хранилище.

**Следующая итерация:** взвести precapture-триггер на билдере превью, переотправить
повторяющийся запрос, дождаться сходимости AE и захватить **тот же билдер**. Если `.lri`
ляжет — вопрос закрыт.

## Панхром есть в каждом снимке, солвер уже написан

**Какой панхром попадает в снимок** (перепись всего корпуса, 273 `.lri`, `light gather`,
15.10.2026):

| фокусное снимка | снимков | панхромный модуль в `.lri` |
| --- | --- | --- |
| 28–69 мм | 213 | **A2** во всех |
| 70–150 мм | 60 | **C6** во всех, в том числе 14 снимков на 149 мм |

Панхромный план снимается тем же спуском, что и цветные, — без правки HAL и root. Живого
потока с него нет: превью и видео — кроп A1 (`hal-patching.md`). Значит рабочий сценарий —
пробный кадр, вынуть из `.lri` только A2 (4160×3120, 10 бит, ~16 МБ) и разобрать на камере.
Комментарий в `MonoMode.java` («на 35, 50 или 70 мм панхромный план в `.lri` не попадает»)
корпус опровергает.

**Солвер для A2 есть в `lumina-core`** — Rust без зависимостей, MIT, ветка `feat/lumina-core`
в [lumina-astronomy-software/desktop](https://github.com/lumina-astronomy-software/desktop),
7–14.09.2026:

| что | результат | коммит |
| --- | --- | --- |
| солв A2 | `L16_00241`, поле 63°: 83 пары из 204 источников, масштаб 61,5″/px против заводских 61,09, промах 10′ против astrometry.net | `f4f9ddd` |
| дисторсия L16 | заводские CRA и полином сведены в одну радиальную модель, ≤ 0,5 px; от фокуса не зависит | `ea73f97`, `1947160`, `8f7618b` |
| подсказка направления | место и время из EXIF, высота и зенит из акселерометра, перебор одного азимута: 900 проб, 0,64 с, азимут 318° против 317,8° | `fa77249` |
| деревья в кадре | солверу идут звёзды из чистого прямоугольника неба, но в координатах всего кадра; объекты за преградой помечаются | `c0d84f4` |
| небо светлее деревьев (облако с засветкой над чёрными елями — как на L16) | считаются оба прямоугольника, берётся тот, где больше звёзд: 50 → 108 | `2b18e31` |
| отбраковка ложных решений | доля совпавших от числа находимых звёзд, порог 0,3 | `reject.rs`, `matcher.rs` |
| счёт на L16 | ядро прогнано на L16, совпадение с маком до 1,7·10⁻¹² | `2f0b863` |

Тот же разбор сырых кадров L16 нашёл пьедестал с периодом 4 по столбцам — ошибку распаковки
10 бит в `lightmotiv`, исправленную там же 13.09 (`a8c3660`).

**Из этого следует план:** солвер не писать, а встроить ядро в приложение камеры через JNI.
Наше остаётся одно: перенести найденную WCS с A2 на живое превью A1. Звёзды на бесконечности,
поэтому модули отличаются только поворотом, а он есть в заводской калибровке каждого `.lri`.

## Рядом

[AstroKey](https://github.com/lumina-astronomy-software/companion) — полевой помощник для астрофото:
управление Canon 650D по PTP/USB-host плюс параллельная съёмка широкого поля камерой
телефона. Прототип проверен на живом железе. Light в нём не упоминается; естественное место
для L16 там — третий бэкенд рядом с `cameralink` и `phonecam`. Канал связи открыт: полный
контроль даёт adb с интентами `CITEST_INTENT` (нужен компьютер), беспроводной спуск —
BLE HID, повторяющий гимбал (подтверждено, что кнопка гимбала работает).
