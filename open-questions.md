## Захват: как на самом деле делается снимок

- [x] **Привилегии для полного захвата не нужны.** Наша сборка стоит в `/data/app`, а не в
      `/system/priv-app`, и снимает кадры на 163 МБ. Пробник с нуля (`astro-probe/`) обычной
      установкой открывает камеру, собирает сессию и ведёт превью 3840×2160.
- [x] **Вендорные теги доступны рефлексией, но не перечислены.** В
      `getAvailableCaptureRequestKeys()` их ноль; штатный SDK собирает их через скрытый
      конструктор `CaptureRequest.Key(String, Class)`, на Android 6 это не запрещено.
- [x] **HAL объявляет выдержку 10 449 … 29 981 853 000 нс, ISO 100…12800 и предел
      аналогового усиления ISO 775.** Последнее совпало с замером по кадрам (7.75×).
- [ ] **Где стоит предел 19.45 с.** HAL объявляет 29.98 с, интерфейс показывает 29.98 с,
      в кадр пишется 19.45 с. Ограничение лежит ниже HAL — найти где.
- [ ] **Чем запускается захват шестнадцати модулей.** Одиночный `capture()` по шаблону
      `STILL_CAPTURE` не годится: перебраны `CONTROL_CAPTURE_INTENT` = 2 и 6…13 вместе с
      `co.light.stacked_capture_state`, кадра нет. По коду штатного приложения спуск — это
      захват **билдера превью** после взведённого `AE_PRECAPTURE_TRIGGER`; проверить.
- [ ] **Можно ли задать произвольный состав модулей.** 2026-10-15: в HAL есть `capture_mask`, он уходит в CCB (`issue ccb cmd … capture mask: 0`); найти, откуда приложение может его выставить. Сейчас группы берутся парами
      (`frame_size_ab`, `frame_size_bc`, `frame_size_c`), поэтому A2 и C6 в один кадр не
      попадают никогда.
- [ ] **Что такое `co.light.tripod_fw`** — ключ результата, камера сообщает состояние штатива.
- [ ] **Почему A1 экспонируется иначе остальных** — усиление 3.88× против 7.75×. Для
      сложения по пространству это дефект. 2026-10-15: A1 — источник превью и видео (кадр
      видео — центрированный кроп A1, `log/2026-10-15.md`), вероятно, поэтому его ведёт
      свой AE.

      Заводские отношения каналов гуляют в пределах 5% (`rg` 0.472…0.516, `bg` 0.650…0.711) —
      это экземплярный допуск, а не другие фильтры.
- [x] **Колориметрия у каждого модуля своя и постоянна.** Три осветителя — D65, A, F11.

- [x] **Группы работают не так, как я записал раньше.** В кадре 28 мм участвуют пять A и
      пять B, в кадре 103 мм — пять B и шесть C. То есть A/B/C — это фокусные самих модулей,
      а не разбиение по тому, кто снимает какой кадр; B участвует в обоих.
- [x] **Уровень сигнала между модулями: не экспозиция.** `CameraModule` несёт
      `sensor_exposure` и `sensor_analog_gain` на каждый модуль, `lri-mono --census` их теперь
      читает. Они почти одинаковые: 30.42 мс у всех, усиление 6.5× у всех, кроме опорной A1 с
      3.25×. После нормировки внутри группы 28 мм цветные дают 0.51…0.67, монохромный A2 —
      1.18, то есть **ровно вдвое, один стоп**. Прежний пятикратный разброс весь пришёлся на
      группу B: это 70 мм, каждый модуль кадрирует свой кусок сцены. Остаётся стенд —
      но уже не для этого вопроса, а для виньетирования и поля зрения.

      Со стенда — плоское поле:
      - ровная матовая стена или большой лист, равномерно освещённый, с расстояния 2–3 м,
        чтобы в кадр самого широкого модуля не попадало ничего кроме неё;
      - лёгкая расфокусировка, чтобы фактура стены не мешала;
      - режим `manual` с зафиксированными ISO и выдержкой, чтобы запрос ко всем модулям был
        одинаковым; если уровни всё равно разъедутся — значит экспозиция раздаётся модулям
        независимо, и это ответ на главный вопрос;
      - три уровня освещённости, отличающиеся примерно вдвое, чтобы проверить, ходят ли
        уровни модулей синхронно;
      - этот же кадр закрывает виньетирование и падение резкости к краям, а на широком —
        вопрос про обрезку поля зрения.

      Со стенда — мира: снять с известного расстояния, посчитать реальное поле зрения каждого
      модуля и сравнить с заявленным ЭФР. Это прямой замер того самого кроп-вопроса: 16.6 мм
      против выдаваемых 28.
- [x] **Выигрыш монохромного модуля** по двум кадрам: A2 даёт 233 против среднего 108 у
      цветных (1.1 стопа), C6 — 206 против 118 (0.8 стопа).

## Движок Light вызываем с десктопа

Внутри `Lumen.app/Contents/Frameworks/` лежит **`libcp.dylib`** — та же библиотека
вычислительной фотографии, что и в галерее на камере, но собранная под macOS x86_64 и,
в отличие от андроидной, с нормальной таблицей символов. Поверх неё публичный C++ API
`CIAPI`:

```text
CIAPI::Renderer::Create(RendererProfile)
CIAPI::RendererBase::setInputDataStream(const void*, unsigned long)   ← сюда байты .lri
CIAPI::RendererBase::setProperty / getProperty (ParamInt, ParamFloat, ParamString, …)
CIAPI::Renderer::render(int, ROI, RenderType, bool)
CIAPI::Renderer::outputBuffer()
CIAPI::Transform  — кроп, поворот, соотношение сторон
CIAPI::StateFileEditor, CIAPI::DepthEditor  — состояние снимка и правка глубины
```

Имена свойств лежат строками: `exposure`, `contrast`, `clarity`, `saturation`,
`sharpening`, `vibrance`. `MonoFusion` и `SensorType::Panchromatic` — там же.

Проверено: библиотека **грузится на Apple Silicon под Rosetta** (рядом нужны
`libceres.dylib` и `liblricompression.dylib` из того же каталога), символы
`GetVersion`, `Renderer::Create`, `setInputDataStream`, `outputBuffer` разрешаются.

- [x] **Харнесс написан — Grok, 05.08.2026.** `.lri` → картинка родным движком, сверено с
      кэшем Lumen (MAE≈11, r≈0.98). Рецепт и путь — `GROK.RESEARCHES.md` § A1. Проверки
      лицензии не встретилось; профиль рендера задаётся в `Create(...)`.
- [x] **Экспозиция и усиление на модуль** оказались доступны и без движка — прямо из
      контейнера, `lri-mono --census`.
- Дальнейшая десктопная работа живёт в отдельном репозитории **luminat**, не здесь.
  Вариант Г из `monochrome.md` закрыт с той стороны.

## JPEG на камере — это прокси, а не снимок

- [x] **Сохраняемый JPEG всего 1440×1080.** Проверено на обоих сегодняшних кадрах,
      `L16_00181.jpg` и `L16_00182.jpg`: 1.5 Мп при заявленных в HUD 13 и 52. То есть камера
      кладёт рядом с `.lri` лишь превью, а полноразмерный снимок собирается позже — галереей
      или Lumen из контейнера.

      По мануалу уровней три: превью при съёмке, **13 Мп сборка на камере** и **52 Мп в
      Lumen**. То есть снимок рождается не в момент спуска, а при сборке из контейнера.

      Почему именно так — выяснено (Grok, `GROK.RESEARCHES.md` § D): движок один и тот же,
      разница в **`RendererProfile`**. Мобильный `Create(1/2)` даёт 13 Мп, десктопный
      `Create(3)` — полотно 10432×7824. То есть 13 Мп на устройстве это продуктовый и
      тепловой предел, а не «модули больше не пишут»; в мобильном профиле super-res просто
      отключён строкой `This profile doesn't support super-resolution`.

      Это меняет формулировку претензии к монохромному режиму: он отдаёт не «цветной снимок
      вместо чёрно-белого», а **цветное превью**, тогда как настоящий кадр в любом случае
      рождается из `.lri`. Значит путь через `--peek` не обходной, а основной, и вопрос
      «почему JPEG цветной» частично снимается сам.

      Симметрия, которую стоит держать в голове: план монохромного модуля — 4160×3120, те же
      13 Мп, что собирает камера. Только у сборки они получены склейкой и дебайеризацией, а у
      A2 напрямую, без единой интерполяции.

      и лишь затем передаётся их обработчику — поведение приложения не меняется.

      Две ловушки по дороге, обе стоили времени: HockeyApp регистрируется **не** синхронно из
      `onResume`, а через собственный хендлер, и приземляется поверх нас — поэтому захват
      перепроверяется через 5 секунд. И **исключения с главного потока куда-то деваются**:
      брошенное в `postDelayed` не роняет приложение и не доходит ни до одного обработчика.
      Проверять сеть нужно с фонового потока; флаг `crash.selftest` в `features.prop` делает
      это одной перезагрузкой.

## Управление гимбалом: ветка упирается в один разъём

Спуск с гимбала уже работает по HID, но это весь канал. Всё, что богаче — движение по осям,
запись и воспроизведение траекторий — существует, и протокол **опубликован самой DJI**:
«DJI R SDK protocol v2.2». Три независимых открытых проекта его используют, и все три идут
**проводом в порт RSA по CAN**, ни один не трогает Bluetooth:

- [ConstantRobotics/DJIR_SDK](https://github.com/ConstantRobotics/DJIR_SDK) — RS 2, CAN через
  USBCAN-II: `move_to`, `set_speed`, `get_current_position`, все три оси, шаг от 100 мс.
- [rileyharmon/DJI-Ronin-RS2-Log-and-Replay](https://github.com/rileyharmon/DJI-Ronin-RS2-Log-and-Replay)
  — RS2 и RS3 Pro, CAN через CANable: запись и воспроизведение движений плюс мотор фокуса.
- [MrColoo/DJI-Ronin-Remote-Controller-ESP32](https://github.com/MrColoo/DJI-Ronin-Remote-Controller-ESP32-ESP8266)
  — Ronin SC, ESP32 в порт SBUS, только панорама и наклон.

- [ ] **Решающая проверка не программная: есть ли на RS4 Mini порт RSA или CAN.** По
      документации DJI у Mini упоминается только NATO, RSA описан для полноразмерного RS 4.
      Смотреть на корпус.
- [ ] Если порт есть — вырисовывается моушен-таймлапс без всякой интеграции: компьютер по CAN
      проигрывает записанную траекторию, камера снимает сама, спуск уже идёт по HID-клавише.
      Синхронизация нужна только по времени. С камеры напрямую не выйдет: её USB — порт
      устройства, не хоста, понадобится посредник вроде ESP32.
- Мобильный SDK DJI тут не поможет: он про дроны (Mavic 3 Enterprise, M30, M300 RTK),
  RS-серии в поддерживаемых нет, плюс требует активации ключом.
